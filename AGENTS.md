# PLANETARY-SCALE MULTI-SUBJECT INVARIANT — read before designing ANY solution

**This block is a top-priority rule. It applies to every solution any agent designs, builds, reviews, or ships — backend, frontend, infra, data, or doctrine.**

Every solution must serve **any subject at planetary scale** — any user, any agent, any wallet, the 1,000,000th and a fresh-random one — **identically and with cost sublinear in the number of subjects**. Never just the founder's wallet, never a hand-picked cohort. A solution that only works for the founder, for a capped/allowlisted set, or whose cost grows with the user count, is **not done** — it is a defect, even if it "works" in a demo.

## The 5-question gate (a solution is NOT shippable unless every answer is "yes")
1. **Nth-subject:** Does it serve an arbitrary new subject with **zero** special-casing? (No hardcoded founder address, no `if (user === founder)`, no per-subject branch.)
2. **Sublinear cost:** Does compute / RPC / DB / $ stay ~flat as subjects grow 44 → 1e6? (**No** `listActive`/`listAll`/`SELECT * … <subjects>` inside a timer; **no** `Promise.all` / `for` over an unbounded subject list on a cycle.)
3. **No gate:** Is there **zero** allowlist / cap / `*_CAP` / `*_ALLOWLIST` / `*_WHITELIST` / `*_OVERRIDES_JSON` / `*_FOUNDER_*`? (These are **deleted**, not exempted, not "temporary build-mode stopgaps".)
4. **Push not pull:** Is each per-subject read triggered by an **event** — chain webhook, user attention (session/SSE), agent action (bus envelope), or explicit `/refresh` — with polling **OFF by default** and only a degraded reconciliation fallback?
5. **Cohort + receipt:** Do you read the subject set via **`cohort.query(name)`** (bounded, indexed, event-fed — not a full scan), and does every user-visible number carry a `receipt_id` linking to its bus envelope (receipt-or-it-didn't-happen)?

## What good vs bad looks like
- **BAD:** `setInterval(() => { for (const u of await listActive()) read(u) })` · `MONEY_TRUTH_CANONICAL_WALLET_CAP` · `const FOUNDER = "AQHCs…"` · `STAGE_1_FOUNDER_CAP_USD` · a number on screen with no receipt.
- **GOOD:** Helius/chain webhook → update exactly the one changed subject → bus → SSE · `cohort.query("attention_received")` · per-user on-demand read, edge-cached · shared reserve/price read once per TTL, not per subject · empty result still emits `count=0` envelope.

## If a solution can't pass the gate
It is not "ship now, scale later." Redesign it to be planetary-correct, or — if that is genuinely a one-way door or >Class-A cost — escalate via EA (per the KERNEL-LOOP rule). "It works for the founder" is **not** acceptance.

## Enforcement (awareness → detection → penalty), same regime as BUS-FIRST
1. **Awareness** — this block (every agent reads it at session start) + `kernel/docs/doctrine/planetary-substrate-invariants.md`.
2. **Detection** — the `planetary-substrate` CI lint (`iac/lints/planetary-substrate/`, PLANETARY-001..010) blocks PRs that reintroduce a banned pattern, citing the doctrine line. The **random-cohort probe** (`po/scripts/planetary-substrate-probe.ts`) is the runtime fitness function — a **fresh-random-wallet failure is a P0** (correctness is proven on random + freshly-minted subjects, never a founder/TY allowlist).
3. **Penalty** — a detected bypass downgrades the offending agent's `capability_tier`, blocks PR merges via the planetary gate, and is logged as a durable incident. Repeat bypass escalates to sentinel.

## Dispatch OODA loop — daemon-managed (build mode)

You (this agent) are running inside a repo that has a **local filesystem daemon** watching `intake/pending-dispatches/` for new `.md` files. When a file lands, the daemon passes the file contents to the configured local runner. The default runner is Claude via `AGENT_RUNNER=claude`, which invokes `claude -p` in this repo. Local Codex is also supported via `AGENT_RUNNER=codex`, which invokes `codex exec` in this repo. If this prompt reached you through either path, you are that runner session.

**Cadence:** event-driven via `fswatch` + 1-minute idle poll as a belt-and-braces. Typical dispatch → response latency: 30-120s.

### Dispatch SLA (founder mandate 2026-05-18 — hard contract)

For **every** dispatch on **every** transport (filesystem today, GitHub Actions relay and pubsub bus later):

1. **60-second ack.** Within 60s of the dispatch file landing, the agent's daemon MUST commit `intake/responses/<basename>.ack.md` stating it picked up the work. Today `scripts/agent-daemon.sh` does this automatically before invoking the runner — you don't have to do anything extra in normal flow.
2. **5-minute resolution-or-status.** Within 5min of pickup, EITHER the full response file MUST be committed OR a `intake/responses/<basename>.status.md` MUST exist saying `status: in_progress` with `updated_at` < 5min ago. The daemon's background status emitter rewrites the status file every 300s; if you take a complex action that runs longer than 5min, the status keeps refreshing automatically as long as the daemon is alive.
3. **5-minute re-status.** If the work is still in flight at the 5-min mark, the status file MUST be refreshed every 300s thereafter. Silence past a 300s interval is a hard breach.

Any breach is a P0 incident — `scripts/sla-watchdog.sh` runs every 60s, reports breaches to `reports/dispatch/sla-breaches-<DATE>.md`, and restarts the responsible daemon. Full contract: `coordinator/data/sla.yaml`.

If you're acting as the runner inside a long-running dispatch and you realize the work will exceed 5 min, write a one-line `.status.md` yourself rather than waiting for the daemon's 5-min refresh — it's cheap, it gives downstream auditors visibility, and it documents WHY the work is taking the time it is.

### Runner architecture

- **Transport is model-agnostic.** `scripts/dispatch.sh` writes Markdown dispatches into `intake/pending-dispatches/`; responses still land in `intake/responses/<basename>`; processed dispatches still move to `intake/processed/<YYYY-MM-DD>/<basename>`.
- **Execution is runner-specific.** `scripts/agent-daemon.sh` owns the watcher and dispatch protocol. It selects execution with `AGENT_RUNNER`, defaulting to `claude`. `scripts/claude-daemon.sh` remains a compatibility wrapper for existing launchd/supervisor paths.
- **Local Codex is a repo-local runner.** `AGENT_RUNNER=codex` runs `codex exec --cd <repo>` with `AGENT_CODEX_SANDBOX` defaulting to `workspace-write`, then writes Codex's final message into `intake/responses/<basename>`. Optional `AGENT_CODEX_MODEL` and `AGENT_CODEX_PROFILE` pass through to `codex exec`. It uses the local Codex CLI auth/config, not the GitHub issue connector.
- **Manual/noop mode is explicit deferral.** `AGENT_RUNNER=manual` or `AGENT_RUNNER=noop` writes a clear `Status: deferred` response instead of invoking a model. Use this when Claude quota is exhausted or no local model runner is available.
- **Codex Cloud is separate.** `scripts/codex-dispatch.sh` opens a GitHub issue with an `@codex` mention so the GitHub Codex Connector can work in Codex Cloud. It is not the repo-local daemon path, is separate from `AGENT_RUNNER=codex`, and does not consume `intake/pending-dispatches/`.
- **Artifact lifecycle is separated from memory.** Raw dispatch files, response files, ack/status files, and runner transcripts are transport exhaust. The daemon archives raw copies under `$AGENT_DAEMON_ARCHIVE_ROOT` (default `~/.toreva/agent-daemon/archive`) and these paths are git-ignored. Distilled lessons and decisions belong in repo-local `MEMORY.md`; cross-repo candidates are promoted by the memory agent for kernel consumption.

### Document safety

Before writing, replacing, formatting, flattening, exporting, or regenerating any user-facing document or active working file, apply this fleet-wide safety rule:

- **Treat user-open files as read-only.** If the user has a file open in an IDE, Preview, Acrobat, Office, a Google Drive sync folder, or has just said they are working in it, do not overwrite that path.
- **Ask before replacement.** Do not regenerate, copy over, format, flatten, or export over an existing user-facing document unless the user has expressly requested that exact overwrite.
- **Default to versioned output.** Write a new file such as `_v2`, `_patched`, `_review-copy`, or a timestamped filename instead of replacing the existing file.
- **Preserve before approved overwrite.** If the user explicitly approves replacement, first copy the current file to a recovery/backup path with a timestamp, then write the replacement.
- **Handle binary and office-style files conservatively.** PDFs, forms, spreadsheets, word-processing documents, and synced documents may contain manual edits that are not recoverable from git; once manual editing has started, programmatic regeneration is not safe by default.
- **On overwrite incidents, stop writes.** Preserve the current disk state, look for backups/autosaves/history before touching the file again, and communicate plainly about what happened and what recovery options exist.

### Your OODA loop when invoked from a dispatch

**Observe.** Read the dispatch file. It has canonical headers (`Status`, `From`, `To`, `Priority`, `Raised`, `Fallback reason`). Below the headers is the ask (`## Ask`) and notes (`## Notes`).

**Orient.** Scope check:
- Is the `To:` field pointing at this repo / agent? If not, stop and write a short explanation to `intake/responses/<basename>` noting mis-routing.
- Is the ask inside your `write_scope` (per `iam/data/agent-registry.yaml`)? If not, decline with reason.
- Is it a P0? Prioritize over other work.

**Decide.** Choose one of:
1. **Action it now** (most common). Do the work in-repo: write code, run tests, query BQ, publish a bus envelope, whatever the ask requires.
2. **Escalate.** If the ask exceeds your scope or needs approval, dispatch to your accountable agent via `coordinator/scripts/dispatch.sh --to <accountable> --title "escalation: ..." --body-file -`.
3. **Defer with reason.** Write a response explaining what's blocking and expected unblock time.

**Act.** Execute. If the action involved code changes, you MUST complete the full commit-to-deploy chain BEFORE writing the response (see "Commit-to-deploy SOP" below — founder mandate 2026-04-24, re-affirmed 2026-05-16 after the identity dispatch left uncommitted work in the worktree).

Write the response file to `intake/responses/<basename>` with:

```markdown
# Response to: <dispatch title>

**In reply to:** `intake/processed/<date>/<basename>`
**Responded:** <ISO timestamp>
**Status:** completed | in_progress | escalated | declined | deferred

## Summary
<1-3 sentence TL;DR>

## Work done
<bullet list of concrete actions — file edits, PRs opened, BQ queries run, bus envelopes published>

## Blockers / follow-ups
<if any>
```

**Move the original.** Once you've written the response, the daemon will move `intake/pending-dispatches/<basename>` → `intake/processed/<YYYY-MM-DD>/<basename>` automatically. You do not need to do that yourself.

### Commit-to-deploy SOP — REQUIRED before declaring Status: completed

Founder mandate 2026-04-24, re-affirmed 2026-05-16: **review / commit / merge / deploy must NEVER require manual triggering after the daemon runs.** Writing files and exiting is incomplete work. The runner session is responsible for the full chain.

If you touched tracked files in this repo as part of the dispatch:

1. **Run tests + typecheck** appropriate to the repo (e.g. `npm test`, `pnpm typecheck`, `pytest`). Do NOT mark `Status: completed` if they fail — escalate or defer.
2. **Create a branch** named `daemon/<agent>/<short-dispatch-slug>-<YYYY-MM-DD>` (or rebase your work onto one if you've been working on main).
3. **Commit** with a descriptive message. End the commit message with a trailer:
   - `Spawned-By: <plan-agent-id>` if acting on a planning-agent tick, OR
   - `Dispatched-By: <from-agent>` otherwise
   - Plus the standard `Co-Authored-By:` if applicable.
4. **Push** the branch to `origin`.
5. **Open a PR** via `gh pr create` with a body referencing the dispatch path.
6. **Enable auto-merge** via `gh pr merge --squash --auto` so CI can land the change without further human action. If `--auto` fails with `enablePullRequestAutoMerge` / "Protected branch rules not configured for this branch", the target branch has no branch-protection rules, so GitHub cannot arm auto-merge regardless of the repo-level `allow_auto_merge` setting. Fall back as follows: if the PR has checks (`gh pr checks <pr>` lists any), wait for them with `gh pr checks <pr> --watch` and then merge directly via `gh pr merge --squash`; if no checks are configured, merge directly via `gh pr merge --squash` immediately. Do NOT add branch-protection rules inline to make `--auto` work — that is a deliberate per-repo governance change (a required status check on a repo with no CI deadlocks every future PR), so dispatch coordinator instead if you think a repo needs protection rules.
7. **Verify CI is green** (or at least running with no immediate failures) before declaring completed.
8. In the response's `## Evidence` section, include: branch name, PR URL, commit SHA, and CI status link.

If you wrote code but couldn't commit (lint errors you can't fix, missing credentials, repo policy block), use `Status: deferred` and explain in `## Blockers / follow-ups` what's needed.

**Why this matters:** the daemon system is supposed to be commit-to-deploy end-to-end. Leaving files in the worktree means PO or a human has to manually commit, which breaks the agent-autonomy contract.

# AGENT FAILURE MODES AND METACOGNITION — READ BEFORE CLAIMING ANYTHING IS DONE

**Fleet-wide doctrine. Origin: po, 233 incidents → 2026-08-25. Kernel adoption: 2026-08-25.**
**Every lesson below was paid for with a real defect that reached the founder.**

## The six failure modes

**MODE-001 — measurement-at-the-wrong-layer (41 incidents)**
Checking that a field is FILLED rather than that the claim is TRUE.
*Rule:* verify the substrate the claim is about, not a record describing it.

**MODE-002 — control-without-an-edge (39)**
The artefact exists and is CORRECT and nothing consults it.
*Rule:* a control exists only if something mechanically refuses on it. Prove it runs against known-bad input.

**MODE-003 — the-arrival-gap (35)**
Send ≠ arrive. Merge ≠ deploy. Deploy ≠ serve. Dispatch ≠ pickup ≠ model-ran ≠ work-done.
*Rule:* verify at the END of the chain, and enumerate the chain first.

**MODE-004 — verified-the-wrong-thing (30)**
Green checks while the product is broken: a proof that reimplements the fix inline, a test seeded with the state it should discover.
*Rule:* a test that cannot fail proves nothing. Run it against the pre-fix state.

**MODE-005 — ownership-and-routing (22)**
The noticer becomes the owner; accountability quietly transferred by "passing this to X".
*Rule:* check the registry before touching a path. Delegate responsibility, never accountability.

**MODE-006 — acted-instead-of-diagnosed (15)**
Restarting or re-dispatching because acting feels like progress.
*Rule:* if a manual action must be REPEATED, something already owns it and is failing. Read the incumbent log first.

## Three meta-invariants beneath all six

- **M1 — check the territory not the map.** Modes 1, 3, 4 are one error: consulting a representation instead of the thing.
- **M2 — naming is not wiring.** Modes 2, 5 are one error: a control or owner that exists as prose.
- **M3 — read the incumbent before acting.** Mode 6. The OPERATE path is not guarded; that is why the worst mistakes are operational.

## Eight meta-meta rules (how the learning itself fails)

- **MM1** Record the INVARIANT and the ENUMERATION, never the single instance. *Companion — fixing-instance-ships-class-forward:* after a fix, name the shape and walk the rest of the path before claiming completion (CLASS-018). A finding that names N lines is a sample of that class, not its extent: grep the repo for the property first, and do not read a recurring finding as a failed fix until the attempts are partitioned by terminal state (delivered vs never ran). If you cannot state the invariant plus its enforcement point, you have not found the class yet.
- **MM2** Metacognition is dispatched exactly like a defect class. Reflective learning that stays local is a defect in the learning system. Channel: `coordinator/scripts/dispatch.sh --to kernel` with `metacognition.reflective_lesson` in body.
- **MM3** Every lesson names a number it should move. If the ratio has not moved, the lesson has not landed. Tracked in `data/failure-class-store/repeat-class-report-YYYY-WNN.json` → `mode_repeat_rates`. *Companion — invisible-effect rule:* An instruction whose effect the actor cannot observe decays to zero — not forgetting, no feedback edge. Wire it or expect 0%. *Companion — unmeasured-channel-yield:* sent is motion, landed work is arrival; before reporting delegated work as "with owners", measure far-side channel yield (CLASS-021).
- **MM4** Prefer wiring an existing thing over building a new one. If the remedy is new machinery, say why the incumbent could not be wired.
- **MM5** On naming a failure class, immediately run it against your own loop — it is almost always there. The auditing system is the one system never audited. *Fix pattern:* enforce at DECISION TIME in the actor's own path (hooks, gates), not in a document the actor reads and ignores.
- **MM6** Before verifying anything, ask two questions: (1) Is my method in the same modality as the thing being judged? (2) Does my oracle come from an independent source of truth — not from the artifact under test? A check that cannot fail is decoration, not a control. *Companion — circular oracle:* extracting expected values from the artifact being verified produces a proof that the code shipped is the code shipped — it can never fail. *Companion — bespoke-probe-unvalidated-oracle:* a fresh probe must prove it can pass known-good input before its verdict is trusted on unknown input (CLASS-019). *Companion — negative-result admissibility (CLASS-019 addendum, audit app-1442 2026-09-20):* a negative verification result ("cannot admit X", "cannot bypass Y") is admissible only alongside a positive control that admits on the same harness, and the refusal reason must name the property under test — `STALE` / `UNKNOWN` / "not open" on a case meant to prove a finding is a false green from an early-bail precondition shadowing the logic under test. Build the probe control-first. Doctrine and classifier aliases only; one instance, nothing mechanically refuses a negative suite that lacks a control. Wire a modality-native instrument first (MM4); a missing instrument is CLASS-015 (founder-proposed capability never built), not a reason to substitute a cheaper modality.

- **MM7** When building or reviewing any loop, name which step is still a person and what happens the day they are busy. A loop whose last step depends on someone remembering is not a loop; it ends at that person. Publish the human step with the loop, and treat an unnamed or placeholder human step as an open finding (CLASS-027).

- **MM8** Before serving a claim that work is happening, ask what substrate can change the object without the person. Proposal, intent, rendered text, local state, and decomposer output are not activity; render the weaker true state unless a receipt, scheduled wake, durable run, system-of-record write, bus envelope, runtime entrypoint, or observable third-party state exists (CLASS-033). If the same agent wrote the code and the probe, require evidence of a different kind from the claim artifact or an independent probe (CLASS-034).

- **Channel-yield rule (CLASS-021)** Before concluding "it is with the owners", prove the channel is carrying on the far side: sent, arrived, substantive/accepted, rejected/malformed/blocked/deferred/no-run counts, threshold, and repair owner.

- **Gate-incentive rule (CLASS-022)** Before shipping or citing any validator, scorer, gate, checklist, or acceptance criterion, ask what the cheapest way to pass is. If the cheapest pass is fabricated evidence or suppressed truth, the gate selects for lying and must be corrected.

- **Product-schema question rule (CLASS-020)** A question a person cannot answer from their own world is a defect. Do not ask users to resolve Toreva record types, field names, or taxonomy labels; ask a world-shaped question or route the internal classification to its owner.

- **Arrival-assertion rule (CLASS-024)** Before `Status: completed`, name the receiving-system fact that would be false if the work never arrived. "I produced X" is authoring evidence, not arrival proof.

- **Loop-human-step rule (CLASS-027)** Before shipping or reviewing any loop, answer: which step here is still a person, and what happens the day they are busy? An unnamed human step is an open finding.

- **First-token hot-path rule (CLASS-049)** For any session-facing loop, enumerate what stands between the person's words and the first useful token. Governance gates actions, not ordinary shaping words; batch wake/tick loops are background-only; clarification must be in-session unless the loop names an explicit open gap; independent pre-checks before the same consequential call run concurrently; tests pin check-before-act plus refusal codes, not serial `await <check>` order.

- **Effort-metric rule (CLASS-051)** When a control reports health, ask what it measured. If it measured effort (sent, recorded, attempted, escalated), it measured nothing. Three tells: (1) the metric counts events the actor emits, not states the world reaches; (2) a status word is accepted without the artefact it asserts; (3) a field exists that nothing branches on. A fleet that fixes this class in its work but not in its controls keeps shipping green gates over dead loops.

- **Structure-is-evidence rule (CLASS-052)** Before any intent compiler, decomposer, or planner creates multiple governed objects from an input, ask: was decomposition explicitly requested, or inferred from formatting? Newlines, bullets, headings, colons, and paragraph breaks are evidence of possible structure, not authority to decompose. The default is ONE object. Decomposition must be earned through explicit user instruction, high-confidence semantic signal, or an ask. Silently decomposing and silently refusing are both failures. The person always keeps their words — a refusal that discards a long paste is the worst available outcome.

- **Duplicate-escalation rule (CLASS-053)** Before raising a new escalation for a chronically-recurring, externally-owned blocker, grep sibling repos' `intake/processed/` and `intake/pending-dispatches/` for the blocked resource's identifier. If a live, non-terminal, in-SLA escalation already exists, cite it and stand down — don't duplicate it. If it has itself breached SLA, escalate that thread's non-response rather than forking a new parallel ask. Re-verifying a chronic blocker on every redrive stays correct and required; only the unchecked "open a new escalation" step is gated by this class.

- **Reroute-loop re-escalation rule (CLASS-061)** Before re-deriving a Class-A analysis or re-filing an escalation on a rerouted plan/exit criterion, grep the escalation target's own `intake/pending-dispatches/` and `intake/responses/` for the criterion name, plan id, or prior dispatch id. If a live unanswered escalation exists, cite it, report the target queue depth/backlog as its own finding, and stand down. If it has breached SLA, escalate that thread's non-response instead of forking a duplicate. Only re-derive when underlying facts changed.

- **Single-tier starvation-guard rule (CLASS-062)** A dispatch/task queue selector that sorts strictly by `(priority, age)` and gains a starvation/aging/freshness guard scoped to only the tier that produced the triggering incident (e.g. a fresh-window discount applied only when `score == 0`) leaves every other tier's identical unbounded-head-of-line-block exposure undeclared until it produces its own incident. Before declaring such a guard complete, enumerate every tier the selector serves; for each untreated tier, either apply the same guard with a tier-appropriate parameter or file a tracked, named follow-up citing the specific tier left open — a code comment asserting other tiers are "unaffected" is not a tracked follow-up. Prefer a staleness signal independent of priority (has the head item's status refreshed within its declared cadence) over repeated per-tier numeric carve-outs.

- **Always-present-field-as-required-key rule (CLASS-063)** A required-input-key check on a scored or routing table (a capability resolver, verb router, tool selector, ranking gate) discriminates only if the field can genuinely be absent on a typical valid input. Gating on a field that is structurally present on every input (a base object field, not an intentionally-optional signal field) degrades the check to always-true, and any registration keyed on it starts matching every task regardless of verb or domain. Before adding a field to a required-input-key list, check whether it can actually be absent; if not, the real discriminator (verb, domain, or a genuinely optional field) must carry the match instead. Run the full sibling-registration test suite before shipping a new scored/routed registration — the failure typically shows up in a sibling's regression tests, not the new capability's own tests.

- **Observation-terminates-in-owner-arrival rule (CLASS-064)** An observation loop is not complete when a report is raised — it is complete when each real owner in a finding batch has received a dispatchable item and a receipt exists that a later tick can read. When a batch spans multiple owners, treating the whole batch as one escalation to one downstream consumer (often the observer's own accountable party) makes the noticer the de facto owner of leaf fixes it does not own, and silently strands every finding whose owner is not that consumer. Before marking a mixed-owner batch consumed: resolve each finding's real dispatchable owner through the canonical dispatch/service registry (never the raw service or HTTP-method string in the finding); fan out leaf findings to their owners independently, keeping only aggregate/self findings bundled to the observer; prove arrival with a named target-inbox artifact, not a bare return code; and write a durable per-owner receipt (`consumed_keys`, `target_agent`, `arrival_path`) that the next tick can read. For a pure aggregate-metric stall, same-tick owner dispatch arrival is terminal for the observer's own escalation path unless another active condition remains or owner arrival fails. If a finding names a repo/checkout basename, continue through coordinator repo basenames plus IAM `agent_id` / `home_repo` / aliases before falling back to the observer.

- **Guard-failure-restructure-not-relaxation rule (CLASS-065)** When a source-text guard, behavioral assertion, or invariant test fails on a change you believe is safe, first restructure the change so the guard passes unmodified. Only if restructuring is genuinely impossible may you argue about the guard, and that argument must be a separate, independently reviewed change — never the same commit or reviewed change as the implementation that needed the assertion relaxed.

- **Current-recovery detector rule (CLASS-066)** An exception detector that can turn red must declare the current recovery fact that makes it green. A true lifetime aggregate may remain in history, but it must not keep paging as active red after the current window has recovered. Split lifetime diagnosis from active exception output, and test old-red-history plus recent-healthy-events as a no-page specimen.

- **Runner-recovery observer rule (CLASS-067)** A detector that claims runner/dispatch work evaporated must classify the runner state and consume the recovery primitive's output before paging. Failure artifacts alone are insufficient: separate expired credential, pre-work capacity refusal, after-start interruption, and true untracked pre-work failure; fresh redrive/backlog/dead-letter state is recovery visibility, while stale, missing, or unreadable state fails closed.

- **Error-cause-attributed-before-reachability-checked rule (CLASS-068)** An error string written by a client names a cause the client cannot know. Before searching inside that named cause — opening a service's application-level handler or refusal-code table — check whether the request reached the application at all: does the response body match the application's own error schema (JSON) or a platform/provider page shape (HTML, generic error page); does an unconditional route at the same origin (`/health` or equivalent) fail the same way; does the platform edge's own state (IAM/invoker policy, load balancer or gateway backend/route configuration) show a path to the application. Only once reachability is confirmed is it correct to read application code for the named cause.

- **Named-decision-match-rederived-not-reverified rule (CLASS-069)** When a dispatch or finding's own preflight (a CHECK3/CHECK3b-style keyword-to-decision match, or an equivalent duplicate-detection step) names an existing decision or control as a likely match, the first two actions are: (1) read that decision in full, (2) re-run whatever proof command it cites against the CURRENT tree — including, for merged-fix decisions, a `git merge-base --is-ancestor <fix-sha> HEAD` check — before writing any new code. Treat "the preflight already found the answer" as a strong prior, not a warning to skim past. If the proof command still passes, the correct response is a duplicate-log entry with fresh proof and a closure dispatch back to the routing agent, never a second, parallel fix for a finding shape that is already closed.

- **Hand-off-claimed-without-dispatch-ledger-id rule (CLASS-070)** A hand-off that a sending half depends on is real only when a dispatch ledger id exists. Cite the `dsp_<hex>` id in the commit/PR body — never the bare word "dispatched" ("is dispatched separately" is an intention written in the grammar of an arrival). An intention is written as an intention ("needs a dispatch to X"). When a two-sided road lands one half at a time, the sending half must fail closed against a receiver that does not yet know the operation, and a test must pin that. `scripts/lint_handoff_claims.py` flags a claim with no id (exit 1) and, with `--verify-ledger`, a cited id with no receipt; it exits 2 UNKNOWN when the ledger is unreadable. The format-only check is passable by inventing an id, so verification must run wherever the ledger is readable. Applies to a signed decision record as much as a commit body (second instance 2026-09-26: GAC DEC-0024 said "Owner dispatches were filed by GAC" 1 to 2 minutes before the four receipts existed; the lint had missed the passive-plural form and now flags it, with a sweep of 0 new hits in about 2,240 commit messages and 2 quoted-example hits in 102 DECs). Nothing runs the lint on decision records unless someone invokes it.

- **Fail-closed-gate-inert-without-verifiable-source rule (CLASS-071)** A fail-closed gate is not safe until it has opened: refusal is what a broken gate produces too, so a stream of refusals is not evidence of strictness. Ship every gate with (1) a measurable opened-at-least-once signal — one `open|refuse` event per decision, refusal reason attached, synthetic opens (stubs, health probes) marked and never counted — and (2) a verifier designed together with a named, deployed, readable record to verify against; if the record does not exist the honest state is implemented-not-serving and its creation is a ledger-id dispatch. Refusal reasons separate "could not verify" (unconfigured, unreachable, malformed) from "verified and rejected"; an unconfigured source is a refusal, never a derived origin. The test double must consult a record fixture and reject a claim the record does not back — a stub that trusts the claim reimplements what the gate exists to distrust. `scripts/check_gate_opened_once.py` reports per gate OPENED / INERT / UNPROVEN / NO_SIGNAL / NO_RECORD_SOURCE and exits 2 UNKNOWN (never pass) on a missing, empty or malformed stream. An open proves the gate opened for something, not the right thing; no gate emits the stream yet, so on the real fleet the checker is UNKNOWN. Corollary (GAC DEC-0024, design instance, no failing incident): a rule that depends on a record no one owns yet must read the ABSENT record as a refusal, and a doctrine sentence is not that record; otherwise it is open by default for the new, unowned case. Serving unproven.

- **Calibrate-a-gate-on-the-spec's-own-exemplars rule (CLASS-072)** Before a gate converted from a written spec is allowed to reject anything, run it over the spec's own ratified reference set and record a per-rule exemplar-pass table. A gate that rejects its own exemplars is mis-set or the spec has an open conflict: report it to the spec owner with the table, never silently loosen. Tier every rule: hard (spec states the number and the gate reproduces it, or the rule cleanly separates exemplars from known-bad) / advisory (measured and recorded, never rejecting) / review (needs eyes; reported as `review`, never `pass`). An unreadable input is a detector failure, not a pass. When building ahead of a promised spec, record every gap-filling choice as a named, reversible assumption (owner, reversal path) so the arriving spec is a diff. If a rejecting gate spends paid work per miss, estimate the reject rate on the exemplars before enabling it. Doctrine and classifier only: nothing mechanically refuses a conversion that skipped calibration, and it is one instance (grammar photo stack). Extends CLASS-019.

- **Prescribed-remedy rule (CLASS-073)** A correct diagnosis does not certify the remedy attached to it. Before applying a remedy a dispatch, ticket or runbook names, run it (or its read-only equivalent) against the exact failing call — same route, identity and origin — after writing the success and failure signals; if the probe fails, do not apply, and take the last-known-good value from a source independent of the brief. After applying, read the outcome from the failing request's own log line or receipt, not the transport status (`deployed` is not serving — a revision pinned by name serves 0%; an HTTP 200 on a stream is not a reply), and look one fault deeper before calling the reported outcome delivered. Doctrine and classifier only: nothing mechanically refuses a P0 dispatch that names a remedy with no probe; one instance (tpa-prod identity outage). Sibling of CLASS-023 / CLASS-068 / CLASS-056.

- **Counterfactual-parent rule (CLASS-074)** Before treating a child (dispatch, PR, blocker) as critical-path work, name which currently-unmet acceptance criterion of its parent would change if the child succeeded perfectly; if none, it is not critical-path work. A signal arriving is not the outcome (ticks stop completing), and a visible blocker is not the parent. Evaluated by `scripts/validate_parent_effect_edge.py` against the parent's own record (admit; `settle` reads the outcome), not by recital. Prototype, not wired at any admission point; two po instances, transfer unproven. Sibling of CLASS-051 / CLASS-018.

- **Two-reader-contract rule (CLASS-075)** A contract with more than one reader is unproven until one real rendering from the real producer has been fed to every real consumer. Producer tests and consumer tests each prove a half and can both be green while the formats are mutually exclusive. A boundary-contract row renders with the real producer, parses with each consumer's real parser at a named ref (not whatever is checked out), finds its consumers by a recorded search rather than memory, exits 0 admitted / 1 refused / 2 unproven (UNPROVEN is never a pass or a refusal), and carries a positive control. Rows live with the producer's owner; kernel supplies the rule and the row shape, not a central registry. Doctrine and classifier only: one incident, reference instrument po#1517 is unmerged, nothing in kernel enforces it. Sibling of CLASS-073 / CLASS-071 / CLASS-056.

- **Control-disposition rule (CLASS-076)** A control's disposition (what happens after it fires) is read from a run that exercised it and the step that consumed its signal, never from its config comment, a flag or a requester's summary. Before acting on "X only reports", find one prior run where X fired and read what happened next; if none exists the disposition is UNPROVEN, not advisory. A step-local `continue-on-error` says the step cannot fail the job; it does not say what the release does, and a later step reading `steps.<id>.outcome` (pre-`continue-on-error`) still acts on the failure. Admission and acceptance are different controls: lifting a hold or gate admission says nothing about the post-deploy oracle that can still roll the change back, so name which link (receipt, admitted, deployed, serving, accepted, retained) an action changes, and a second identical rollback proves nothing. Doctrine and classifier only: nothing mechanically refuses a decision that cites a comment for a disposition; one instance (app#1451, run 35546398242, rollback to 852ab67). Sibling of CLASS-073 / CLASS-071 / CLASS-069.

- **Scheduled-runtime rule (CLASS-077)** A control is verified only under the exact interpreter, PATH and environment of the scheduler that owns it (read from the launchd plist / workflow / image, not your shell); a pass under the developer's interpreter proves the code, not the control. A control with an optional import must, when it cannot load, emit its own degraded finding or return UNKNOWN, never the not-degraded value, or an inert control is indistinguishable from a passing one. A decision that hands a fix to another owner names an arrival predicate (a probe run under the owner's scheduled runtime that is false until the fix serves) and a recurrence trigger; a ledger id is not the arrival (CLASS-070). A lint on `except ImportError: return None` is form-matched (CLASS-057); the property is that the fallback result is indistinguishable from the not-degraded result. Doctrine and classifier only: lint is a candidate with no owner, nothing in kernel enforces it; one instance (po deploy_drift, shape-detector under /usr/bin/python3 with no yaml, fix tested under /usr/local/bin/python3). Sibling of CLASS-055 / CLASS-038 / CLASS-071 / CLASS-070.

- **Probe-passes-then-dies rule (CLASS-078)** A revision's startup probe and its ingress are different edges. (1) A step that runs after `listen` (e.g. Fastify `addHook`, which throws once listening) that throws into `process.exit(1)` passes the platform probe and then dies, so boot tests must wait a settle window after `/health` and assert the process is still alive; asserting alive at the instant `/health` answers races the exit and passes a dying server. (2) A Cloud Run tag URL is its own ingress: `--no-traffic` or a 0% split governs the traffic split only, and a prod env var pointing at a tag URL makes a smoke-only revision a customer dependency; something must watch which revision answered a customer. Doctrine only: one incident (ai-engine DEC-0059), no classifier, nothing in kernel enforces it; the tag-URL detector is `iac`'s.

- **Refusal-names-its-state rule (CLASS-079)** A refusal that cites a limit ("no capacity", "quota", "no runner") must name which state it is in and how it knows: `exhausted` needs a live probe receipt from the current window; `unprobed` (a cached record read as present fact) is UNKNOWN, and UNKNOWN is not FALSE; `unbuilt` (supply exists, no code path reaches it) names an owner and is backlog, not a limit. A refusal that cannot produce the receipt is not entitled to the word. A declared capability with no implementation is worse than none, and a guard installed from a dated instruction must carry that date so it can report it may be stale. Doctrine and classifier only: one incident (po P0 lockout 2026-09-21), nothing in kernel enforces it; po#1569 is the instance control. Sibling of CLASS-038 / CLASS-051 / CLASS-071. - **Never-complete-an-identifier-from-memory rule (CLASS-080)** A commit sha, ledger id, PR number or other opaque identifier that a command or record depends on is copied from a tool's output, never completed from a prefix or recalled. Expand a short ref with `git rev-parse <short>` in the repo that owns it (`git rev-parse --verify <short>^{commit}` to fail on ambiguity) and paste the output; a hand-completed hash is a plausible fabrication and looks identical to a real one. - **Bundled-fix rule (CLASS-054)** Before proposing or accepting one fix for multiple specimens that fail the same check, gate, or test, check each specimen individually against the target contract's own stated scope — existing rulings, falsifiers, documented exclusions — not just whether it currently fails. - **Unit-tested-not-production-reachable rule (CLASS-055)** A passing test that sets a fact-driven rule's precondition by writing directly into a store/fixture proves the logic downstream of that precondition is correct — it proves nothing about whether any real production caller ever sets that precondition. - **Form-matched-not-property-matched rule (CLASS-057)** When writing or reviewing any filter, suppressor, classifier, or gate that decides an instance is bad, name the PROPERTY that disqualifies it before writing the match condition — never match a surface-form proxy (tense, a specific verb, a prefix, the first token of a phrase, an exact string or character encoding). - **Colocated-privilege-self-authorizes rule (CLASS-058)** The unit of privilege is the FILE (or role, or credential), not the job you happen to be adding to it. - **Lookback-without-reconciler rule (CLASS-059)** Any filter of the form "only consider the last N" discards everything older. - **Instrument-distance rule (CLASS-030/031)** Before shipping or citing a surface, route, endpoint, capability, bus topic, or dashboard gate, answer: how many steps short of the person is this instrument, and how many steps short of the consequence it exists to produce? - **Substance rule (CLASS-033)** A user-visible or downstream activity claim must cite substrate that can change the object without the person. `next`, `proposed_move`, rendered copy, local state, and decomposer sentences are proposals or intent, not current activity.

- **No-claim-without-substance rule (CLASS-033)** Any user-visible or downstream-agent assertion of autonomous activity must be backed by substrate that can change the object without the person: a receipt, scheduled wake, durable run, system-of-record write, bus envelope, or observable third-party state. ## Blind-cycle debugging: shortest discriminating run

Founder ruling, 2026-10-22, PO dispatch `d06cccf4c7533c9da8919978`.
This extends MODE-006, M2, MM4 and MM6 across hosted Macs, host daemons,
Cloud Run and every other environment the estate tests or operates.

1. **Shortest discriminating run.** Before each repair/restart/harness cycle,
   write the hypothesis, the cheapest bounded command or probe that can refute
   it, and distinct predicted success and failure signals. Prepare rollback.
   Run that discriminator first; compare actual evidence with the prediction
   and record the delta before the next attempt. A full journey or restart on
   a guess is blind-cycle debugging. Use the full journey only after localising
   the fault, or record why no smaller run can distinguish the hypotheses.
2. **Evidence sufficient to classify in one pass.** Every harness and daemon
   failure record must retain stage, environment and code/run identity,
   timestamps/duration, failure labels, error/exit/response shape, and stable
   correlation hashes or references linking retained evidence. Preserve the
   discriminating structure through redaction and archiving; never retain
   secrets or private payloads to satisfy this rule. A hash alone cannot show
   an error shape. A record that cannot distinguish the competing causes is
   itself an observability defect: fix the producer before spending another
   full cycle. Classify reachability before attributing application causes.
3. **Interactive foothold.** Every operated/tested environment must offer a
   sanctioned read-only probe or attachable diagnostic session, with named
   owner, access scope, invocation, elapsed-time bound and a retained result.
   Reuse the incumbent diagnostic channel. This grants no new credentials,
   write access, or trust-boundary bypass. A missing foothold is a capability
   gap routed to the environment owner, not permission to guess and restart.

**Enforcement contract:** reflective lessons declare `Discriminating run:`
with a bounded runnable probe, hypothesis and opposing signals, and
`Runtime consumer:` with the executable hook/gate path or scheduler label.
The existing daemon response validator must refuse either missing field
independently, including nonterminal responses. `promote: local` must not
bypass this rule for an explicitly reflective lesson. See
`docs/contracts/reflective-lesson-discriminator.md` for owner acceptance tests.
Coordinator owns validator implementation/deployment; Memory owns fleet block
propagation. Doctrine authorship does not certify either arrival.

**Outcome metric:** blind full cycles before classification, median time to
classification, and unclassifiable failure records / sampled failures must
fall; reflective responses accepted without either required field must be zero.
Measure those runtime outcomes separately from contract tests. If the owners
are busy, the runtime change and fleet arrival remain pending, not learned.
